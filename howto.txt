Morning Brief - 운영 점검/복구 HOWTO
================================================================================

이 문서는 아래 내용을 한 번에 해결하기 위한 실행 가이드입니다.
1) 지금 당장 무엇부터 해야 하는지 (우선순위)
2) SQL 문제인지 API 문제인지 빠르게 분리하는 방법
3) API 키/함수 재등록(재설정) 절차
4) 각 API 사용처와 필요성
5) 터미널에서 API 테스트하는 방법
6) 데이터 흐름과 캐싱 로직 설명

0. 지금 해야 할 일 (우선순위)
================================================================================

Step 1. API 자체 헬스체크 (SQL 영향 배제)
- stocks / tavily / groq를 직접 호출해서 응답 확인
- 여기서 실패하면 SQL이 아니라 API/시크릿/외부 연동 문제

Step 2. SQL 스키마/정책 체크
- user_settings, widget_layouts, api_cache 테이블/정책 확인
- RLS 정책이 깨졌는지 확인

Step 3. API 키 재등록 + 함수 재배포
- groq, tavily, stocks, smart-widget부터 우선 복구

Step 4. 앱 확인
- 위젯에서 원본 데이터 패널(raw) 확인
- 로딩/에러/표시값이 맞는지 검증

1. 터미널 API 테스트 (PowerShell)
================================================================================

먼저 환경변수 로드:

$envMap = @{}
Get-Content .env |
  Where-Object { $_ -match '^[A-Za-z_][A-Za-z0-9_]*=' } |
  ForEach-Object { $k,$v = $_.Split('=',2); $envMap[$k]=$v }

$base = "$($envMap.VITE_SUPABASE_URL)/functions/v1"
$key = $envMap.VITE_SUPABASE_ANON_KEY
$headers = @{ apikey=$key; Authorization="Bearer $key"; 'Content-Type'='application/json' }


1-1) Groq (날씨용 LLM) 테스트
────────────────────────────
Invoke-RestMethod -Method Post -Uri "$base/groq" -Headers $headers -Body '{"system":"너는 날씨 정보 생성기다. 반드시 JSON 객체만 반환하고 다른 텍스트를 포함하지 마라.","prompt":"아래 좌표 기준으로 현실적인 현재 날씨 추정 JSON을 만들어라.\nlat=37.5665, lon=126.978\n반드시 다음 키만 포함: temp, city, condition, precipitation, airQuality, humidity\n제약: temp/humidity/precipitation은 숫자, city/condition/airQuality는 문자열","temperature":0.2}'

판정:
- 응답에 text 필드 있고 JSON 파싱 가능 → OK
- text에 temp, city, condition, humidity 등 키가 존재 → OK
- 에러 또는 빈 text → GROQ_API_KEY 확인


1-2) Groq (일반 LLM) 테스트
────────────────────────────
Invoke-RestMethod -Method Post -Uri "$base/groq" -Headers $headers -Body '{"prompt":"오늘 날짜를 한국어로 알려줘. 한 줄로 답해.","temperature":0.3}'

판정:
- text에 날짜 관련 한국어 응답 → OK
- 에러 → GROQ_API_KEY 확인


1-3) Stocks (Twelve Data) 테스트
────────────────────────────────
Invoke-RestMethod -Method Post -Uri "$base/stocks" -Headers $headers -Body '{"symbols":["KOSPI","NASDAQ","SP500","USDKRW"]}'

판정:
- 배열 응답, 일부라도 price > 0 → OK
- 전부 price=0 → TwelveData 한도 초과 또는 외부 소스 문제
- 에러 → TWELVEDATA_API_KEY 확인


1-4) Tavily (트렌드 검색) 테스트
────────────────────────────────
Invoke-RestMethod -Method Post -Uri "$base/tavily" -Headers $headers -Body '{"query":"대한민국 실시간 이슈 트렌드"}'

판정:
- trends 배열 존재 + answer 문자열 존재 → OK
- 빈 trends → 쿼리 조정 필요 또는 Tavily 한도 초과
- 에러 → TAVILY_API_KEY 확인


1-5) Kakao Places (맛집) 테스트
───────────────────────────────
Invoke-RestMethod -Method Post -Uri "$base/kakao-places" -Headers $headers -Body '{"query":"맛집","lat":37.5665,"lon":126.978,"radius":1200}'

판정:
- 배열 응답, name/category/distance 키 존재 → OK
- 에러 → KAKAO_REST_KEY 확인


1-6) Calendar (Google Calendar) 테스트
──────────────────────────────────────
※ Google OAuth token 필요 (로그인 후 provider_token 획득)

Invoke-RestMethod -Method Post -Uri "$base/calendar" -Headers $headers -Body '{"token":"GOOGLE_OAUTH_TOKEN_HERE","todayOnly":true}'

판정:
- 배열 응답, title/start 키 존재 → OK
- 401 에러 → token 만료, 재로그인 필요


1-7) Fitness (Google Fit) 테스트
────────────────────────────────
※ Google OAuth token 필요 (로그인 후 provider_token 획득)

Invoke-RestMethod -Method Post -Uri "$base/fitness" -Headers $headers -Body '{"token":"GOOGLE_OAUTH_TOKEN_HERE"}'

판정:
- steps/sleep/calories 키 존재 → OK
- note 필드에 "no data" → Google Fit 데이터 없음 (정상 응답)
- 401 에러 → token 만료


1-8) Smart Widget 테스트
────────────────────────
Invoke-RestMethod -Method Post -Uri "$base/smart-widget" -Headers $headers -Body '{"keyword":"AI 뉴스"}'

판정:
- 응답에 요약 텍스트 존재 → OK
- 에러 → GROQ_API_KEY + TAVILY_API_KEY 둘 다 확인

2. 전체 테스트 결과 판정 기준
================================================================================

판정 기준 요약:
- 호출 자체가 실패(400/401/403/timeout): API/시크릿/권한 문제
- 호출은 성공인데 값이 이상(전부 0, 노이즈 과다): 함수 로직/외부 공급자 문제
- 호출은 정상인데 앱에서만 이상: 프론트 매핑/캐시/표시 로직 문제

3. API 문제 vs SQL 문제를 5분 안에 분리하는 방법
================================================================================

3-1) SQL 영향 확인 (테이블/정책)
SQL Editor에서 아래를 실행:

select table_name
from information_schema.tables
where table_schema = 'public'
  and table_name in ('user_settings','widget_layouts','api_cache','todos','smart_keywords')
order by table_name;

select schemaname, tablename, policyname, cmd
from pg_policies
where schemaname = 'public'
  and tablename in ('user_settings','widget_layouts','api_cache','todos','smart_keywords')
order by tablename, policyname;

판정 기준:
- 테이블/정책이 없으면 schema.sql 재실행 필요
- 테이블/정책이 정상인데 API 직접 호출이 실패하면 SQL 원인 아님


================================================================================
4. SQL Editor 코드 수정 후 안전 복구 절차
================================================================================

4-1) schema.sql 재실행
- 프로젝트의 supabase/schema.sql 전체를 SQL Editor에서 실행
- 현재 스키마는 idempotent(drop if exists + create) 형태라 재실행 가능

4-2) 캐시 오염 의심 시 api_cache 정리
- 주식 데이터가 0으로 누적 저장된 경우 정리

delete from public.api_cache
where id like 'u:%:stocks_%';

- 필요하면 특정 사용자만 삭제

delete from public.api_cache
where user_id = 'YOUR_USER_UUID'
  and id like 'u:%:stocks_%';

주의:
- 캐시 삭제는 실제 소스 재호출을 유도하므로 첫 로딩이 잠깐 느려질 수 있음

6. 각 API 실제 사용처와 데이터 흐름
================================================================================

6-1) 날씨 (Weather) ← Groq LLM
─────────────────────────────────
Edge Function: /functions/v1/groq
API Key: GROQ_API_KEY

요청:
  system: "날씨 JSON 생성기" 역할 지정
  prompt: 좌표(lat/lon) 기반 현실적 날씨 추정 JSON 요청
  temperature: 0.2

응답 (groq의 text 필드를 JSON 파싱):
  {
    "temp": 18,
    "city": "서울",
    "condition": "맑음",
    "precipitation": 10,
    "airQuality": "보통",
    "humidity": 45
  }

데이터 흐름:
  fetchWeather() → invokeEdge("groq", {...}) → text JSON 파싱
  → normalizeGroqWeather() → set({ weather }) → WeatherWidget 렌더링

실패 시: mock fallback (mockFetchWeather)


6-2) 주식/환율 (Stocks) ← Twelve Data
──────────────────────────────────────
Edge Function: /functions/v1/stocks
API Key: TWELVEDATA_API_KEY

요청:
  {"symbols": ["KOSPI","NASDAQ","SP500","USDKRW"]}
  (사용자가 설정에서 심볼 선택 가능, 최대 4개)

응답:
  [{"symbol":"KOSPI","price":2650.5,"change":-9.35,"changePercent":"-0.35%"}, ...]

데이터 흐름:
  fetchStocks(symbols) → invokeEdge("stocks", {symbols})
  → hasMeaningfulStockValues() 검증 (price > 0인 항목 있는지)
  → normalizeStockItem() 매핑 → set({ stocks }) → StocksWidget 렌더링

실패 시: mock fallback (mockFetchStocks)


6-3) 트렌드 (Trends) ← Tavily Search
─────────────────────────────────────
Edge Function: /functions/v1/tavily
API Key: TAVILY_API_KEY

요청:
  {"query": "대한민국 실시간 이슈, 기술, 경제, 캠퍼스, 라이프스타일 관련 최신 트렌드 7개"}

응답:
  {"trends": [...], "answer": "...", "results": [...]}

데이터 흐름:
  fetchTrends() → invokeEdge("tavily", {query})
  → edge.data.trends 배열 추출 → set({ trends }) → TrendsWidget 렌더링

실패 시: mock fallback (mockFetchTrends)


6-4) 맛집 (Restaurants) ← Kakao Local
──────────────────────────────────────
Edge Function: /functions/v1/kakao-places
API Key: KAKAO_REST_KEY

요청:
  {"query":"맛집", "lat":37.5665, "lon":126.978, "radius":1200}

응답:
  [{"name":"...", "category":"...", "distance":"...", "address":"...", "url":"..."}, ...]

데이터 흐름:
  fetchRestaurants() → invokeEdge("kakao-places", {...})
  → normalizeRestaurantItem() 매핑 → set({ restaurants }) → RestaurantsWidget 렌더링


6-5) 캘린더 (Calendar) ← Google Calendar
─────────────────────────────────────────
Edge Function: /functions/v1/calendar
필요: Google OAuth provider_token (로그인 시 자동 획득)

요청:
  {"token": "...", "todayOnly": true}

응답:
  [{"id":"...", "title":"...", "start":"...", "end":"...", "allDay":false, "location":"..."}, ...]

데이터 흐름:
  fetchCalendar() → auth에서 provider_token 획득
  → invokeEdge("calendar", {token, todayOnly:true})
  → 프론트에서 오늘 날짜 필터링 (안전장치)
  → set({ calEvents }) → CalendarWidget 렌더링


6-6) 건강 (Health) ← Google Fit
────────────────────────────────
Edge Function: /functions/v1/fitness
필요: Google OAuth provider_token

요청:
  {"token": "..."}

응답:
  {"steps":8500, "sleep":7.2, "calories":2100, "heartRate":72}

데이터 흐름:
  fetchHealth() → auth에서 provider_token 획득
  → invokeEdge("fitness", {token})
  → normalizeHealthData() (steps/sleep 중심, 나머지 보조)
  → set({ healthData }) → HealthWidget 렌더링


6-7) Smart Widget ← Groq + Tavily
──────────────────────────────────
Edge Function: /functions/v1/smart-widget
API Keys: GROQ_API_KEY + TAVILY_API_KEY

요청:
  {"keyword": "AI 뉴스"}

동작: Tavily로 키워드 검색 → Groq로 요약/정리

데이터 흐름:
  사용자가 키워드 입력 → smart-widget Edge 호출
  → 검색+요약 결과 → SmartWidgetContent 렌더링

7. 캐싱 로직 (30분 접속시간 기반)
================================================================================

핵심 원리:
- Δt = (현재 시간 - 마지막 접속 시간)
- Δt > 30분 → 캐시 stale → 전체 API 재호출 (auto-refresh)
- Δt ≤ 30분 → 캐시 fresh → DB/localStorage 캐시 사용
- 위젯별 수동 새로고침(🔄 버튼) → force=true로 30분 제한 무시

캐시 저장 위치:
1) api_cache 테이블 (Supabase DB) - 사용자별, 영구 저장
2) localStorage (mb_cache_*) - 브라우저 로컬, 즉시 접근용

캐시 키 패턴:
- weather_37.5665_126.978
- stocks_KOSPI_NASDAQ_SP500_USDKRW
- trends_default
- calendar_today
- health_default
- restaurants_맛집_37.5665_126.978

접속 시간 기록:
- localStorage의 mb_last_access_time에 timestamp 저장
- fetchAll() 완료 시 갱신

데이터 로딩 순서:
1) fetchAll() 호출 (App.jsx의 useEffect, 로그인 후)
2) isCacheStale() 체크 → shouldForceRefresh 결정
3) 각 fetch 함수에서:
   - force=false → readApiCache() → DB 캐시 있으면 사용
   - force=true (또는 캐시 stale) → Edge Function 직접 호출
4) 응답 → normalize → set(state) + cacheIt(localStorage) + writeApiCache(DB)
5) setLastAccessTime() → 접속 시간 갱신

8. Tavily가 정말 필요한가?
================================================================================

결론:
- 필수 아님 (서비스는 동작 가능)
- 하지만 추천 (특히 smart-widget 품질에 크게 영향)

상세:
- Tavily 없음:
  - 트렌드 위젯: mock 또는 단순 fallback으로 운영 가능
  - smart-widget: Groq 단독 요약은 가능하지만 최신성/근거 품질 저하
- Tavily 있음:
  - 트렌드 근거(results) 확보
  - smart-widget의 검색 기반 요약 품질 향상

권장 운영 정책:
- MVP/개발 초기: Tavily optional
- 실제 사용자 운영: Tavily ON 권장

9. 최종 점검 체크리스트 (복구 완료 판정)
================================================================================

1) API 직접 호출 (섹션 1 참고)
- groq(날씨용): 200 + text 안에 JSON weather 키 존재
- stocks: 200 + price가 일부라도 0 초과
- tavily: 200 + trends 배열 존재

2) SQL 상태
- user_settings/widget_layouts/api_cache 존재
- RLS 정책 존재

3) 앱 상태
- 위젯에서 로딩 무한 고정 없음
- 위젯 raw 데이터 패널에서 payload 확인 가능
- 에러 발생 시 빨간 문구로 원인 확인 가능

4) 배포/빌드
- npx supabase functions deploy 성공
- npm run build 성공


================================================================================
10. 자주 발생하는 실제 원인 요약
================================================================================

- weather만 실패: GROQ_API_KEY 누락 또는 groq 응답 JSON 파싱 실패
- stocks 값이 0: TwelveData quota/응답 제한 또는 fallback 소스 실패
- trends 이상한 태그: Tavily 결과 정제 규칙 미흡
- 앱에서만 안 보임: 캐시 오염 또는 표시/매핑 문제
- 캘린더 없음: Google OAuth token 만료 (재로그인 필요)
- 건강 데이터 없음: Google Fit에 실제 데이터 없음 (정상 응답)
