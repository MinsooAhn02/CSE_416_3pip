================================================================================
  Morning Brief 현재 구조 정리 (최신 로직 반영)
================================================================================

작성 목적
- 현재 코드의 실제 동작 로직을 기준으로 구조를 최신화
- 단계별 변경(Selective Loading, 스마트 위젯 파이프라인, AI 브리핑, 고정 TODO)을 반영


1) 전체 아키텍처 개요
================================================================================

[Frontend]
- React + Vite
- Zustand 스토어
  - useAuthStore: Supabase OAuth 세션, 사용자 상태, provider token 보장
  - useSettingsStore: 테마/브리핑/시계 설정 + DB 동기화
  - useWidgetStore: 위젯 가시성/레이아웃/스마트 키워드/스마트 데이터
  - useDataStore: 위젯 데이터 로딩 + API 캐시 + 활성 위젯 선별 로드
  - useTodoStore: 일반 TODO + 고정 TODO(루틴) + 일일 리셋

[Backend Proxy]
- Supabase Edge Functions
  - groq
  - smart-widget
  - tavily
  - kakao-places
  - stocks
  - calendar
  - fitness
  - weather

[DB]
- Supabase 테이블
  - user_settings
  - widget_layouts
  - todos
  - smart_keywords
  - api_cache

[Fallback]
- localStorage 캐시/복구
- mock 데이터 fallback 경로 유지


2) 앱 시작/인증/초기화 흐름
================================================================================

1. App 마운트 시 supabase.auth.onAuthStateChange 리스너 등록
2. 세션 생성 시
   - useAuthStore.handleAuthChange(session)
   - 병렬 hydrate 시도
     - useSettingsStore.hydrateFromDB(...)
     - useTodoStore.hydrateFromDB()
     - useWidgetStore.hydrateFromDB()
3. isLoggedIn === true이면 useDataStore.fetchAll() 실행
4. fetchAll은 user_settings + widget_layouts를 먼저 읽고,
   활성 위젯(activeWidgetIds) 기준으로 필요한 데이터만 선별 호출

참고(계약)
- user_settings는 현재 tone / briefing_length / clock_style / voice_on / vis / persona 기준으로 사용
- settings hydrate는 로그인 후 DB를 직접 조회해 적용

참고
- Supabase 미설정 시 데모 모드로 동작하며 local/mock 경로를 사용


3) 데이터 로딩 로직 (useDataStore)
================================================================================

A. 공통 구조
- invokeEdge(fnName, body): supabase.functions.invoke 래퍼
- API 캐시
  - DB 테이블 api_cache 사용 (user별 key 저장)
  - TTL: weather 10m, stocks 5m, trends 20m, restaurants 20m, calendar 5m, health 15m
- 로컬 캐시
  - mb_cache_* 키에 저장해 graceful fallback 유지

B. Selective Loading
- fetchAll에서 DEFAULT_VIS + user_settings visibility + widget_layouts를 결합
- onboardingProfile, activeWidgetIds 상태를 먼저 세팅
- 활성 위젯에 해당하는 fetch 함수만 Promise.all로 실행

주의
- 위젯 visibility는 user_settings.vis를 기준으로 저장/복원
- onboardingProfile은 현재 persona 중심으로 사용(interest/age는 고정 비어 있음)

C. 위젯별 데이터
1) weather
- DB api_cache hit면 즉시 사용
- miss면 Edge weather 호출
- 실패 시 mock fetchWeather fallback

2) stocks
- DB api_cache -> Edge stocks -> mock fetchStocks 순서
- normalizeStockItem으로 UI 포맷 정규화

3) trends
- DB api_cache -> Edge tavily -> mock fetchTrends

4) restaurants
- DB api_cache -> Edge kakao-places -> mock fetchRestaurants
- normalizeRestaurantItem으로 정규화

5) calendar
- DB api_cache 우선
- provider_token 있으면 Edge calendar 호출
- token/호출 실패 시 mock fetchCalendarEvents

6) health
- DB api_cache 우선
- provider_token 있으면 Edge fitness 호출
- token/호출 실패 시 mock fetchHealthData


4) 스마트 위젯 로직 (useWidgetStore + smart-widget)
================================================================================

A. 클라이언트
- loadSmartWidget(keyword, force)
  - useAuthStore.ensureProviderToken로 token 보강
  - persona + token을 aiService.generateSmartWidgetData로 전달
  - 성공 시 smartWidgetData[kw] 저장
  - 실패 시 smartWidgetErrors[kw] 저장
- SmartWidgetContent
  - generatedData 우선 렌더
  - 없으면 mockSmartWidgets fallback
  - 마운트 시 자동 loadSmartWidget 트리거

B. 서버 파이프라인 (Edge function smart-widget)
- Step 0: route 결정
  - weather/stocks/calendar/fitness/trends/restaurants/none
  - 내부 API로 처리 가능하면 해당 데이터 바로 수집 후 요약
- Step 1: persona 기반 point 3개 생성
- Step 2: Tavily 검색 + Groq JSON 정리
- 최종 출력
  - emoji, sections, lastUpdated, debug 정보


5) 브리핑 로직 (BriefingWidget + aiService)
================================================================================

- BriefingWidget은 mock이 아니라 실제 AI 브리핑 생성 경로 사용
- context 구성
  - weather, stocks, trends, restaurants, calEvents, healthData
  - todos, activeWidgetIds, onboardingProfile
- aiService.generateBriefing
  - 시간대 프로파일(morning/lunch/day/evening)
  - 시그널 점수식으로 상위 3개 선택
  - Groq 호출 프롬프트에 topSignals 포함
  - 출력 3줄 강제(실패 시 local fallback 3줄)


6) 인증/토큰 로직 (useAuthStore)
================================================================================

- login
  - Supabase Google OAuth 시작
  - calendar/fitness scope 포함
- handleAuthChange
  - session 기반 user 상태/로그인 상태 갱신
  - provider_token 저장
  - 사용자 설정 로드(loadUserSettings)
- ensureProviderToken
  - 기존 token 없으면 supabase.auth.getSession으로 재확보 시도

온보딩 저장
- finishOB는 현재 user_settings에 persona를 저장
- 카테고리(selCats)는 localStorage 중심으로 유지

8) Edge Functions 역할
================================================================================

1) groq
- 입력: prompt, system, model, temperature
- 출력: { text }

2) smart-widget
- 입력: keyword, persona, token, 좌표
- 출력: 스마트 위젯 섹션(JSON)

3) tavily
- 입력: query
- 출력: trends, answer, results

4) kakao-places
- 입력: query, lat, lon, radius
- 출력: 장소 배열

5) stocks
- 입력: symbols
- 출력: symbol, price, change, changePercent

6) calendar
- 입력: Google provider token
- 출력: 일정 배열

7) fitness
- 입력: Google provider token
- 출력: steps, calories, heartRate, sleep

8) weather
- 입력: lat, lon
- 출력: temp, humidity, description, city 등
